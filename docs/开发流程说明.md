# 学校 RAG 智能问答系统 - 开发流程说明

> 版本：v1.0  
> 后端：FastAPI + LangChat/LangChain 适配层  
> 前端：Vue  
> 数据库：PostgreSQL + pgvector  
> 缓存：Redis  
> 文件存储：MinIO  
> 一期重点：RAG 准确度、来源可追溯、流式问答、推荐追问  

---

## 1. 总体开发策略

一期开发顺序不是先做完整页面，而是先把 RAG 闭环跑通：

```text
环境和数据表
  -> 文件上传和 MinIO URL
  -> 文档解析
  -> 切片和向量化
  -> 混合召回
  -> rerank 重排
  -> 流式问答 + 来源 URL + 推荐追问
  -> 前端工作台
  -> 评测集和 bad case 调优
```

核心判断标准：
- 能否正确解析资料。
- 能否命中正确 chunk。
- 能否回答并给出文档 URL。
- 能否记录检索和重排过程。
- 能否用评测集持续调参。

## 3. 密钥和配置原则

虽然用户提供了模型 API key，但正式开发不把 key 写死在代码里。原因：
- 避免泄露。
- 方便部署环境切换。
- 方便后续更换模型。

开发时使用 `.env`：

```env
DEEPSEEK_API_KEY=***
DEEPSEEK_BASE_URL=https://api.deepseek.com
CHAT_MODEL=deepseek-v4-flash

EMBEDDING_API_KEY=***
EMBEDDING_BASE_URL=...
EMBEDDING_MODEL=text-embedding-v4

RERANK_API_KEY=***
RERANK_BASE_URL=...
RERANK_MODEL=qwen3-vl-rerank

DATABASE_URL=postgresql+asyncpg://rag:rag@localhost:5432/rag
REDIS_URL=redis://localhost:6379/0

MINIO_ENDPOINT=localhost:9000
MINIO_ACCESS_KEY=minioadmin
MINIO_SECRET_KEY=minioadmin
MINIO_PUBLIC_BASE_URL=http://localhost:9000

JWT_SECRET_KEY=change-me
ADMIN_USERNAME=admin
ADMIN_PASSWORD=admin123
```

`.env.example` 可以提交，真实 `.env` 不提交。

验收：
- `/health` 返回全部 ok。
- 表结构创建成功。
- pgvector 能插入和查询测试向量。
- MinIO 能上传和读取测试文件。

### 阶段 3：文档上传和任务状态

目标：让资料先入库、可查看状态、可追溯文件 URL。

工作内容：
1. 实现文件上传。
2. 校验文件大小不超过 100MB。
3. 写入 MinIO。
4. 生成 `preview_url`、`download_url`。
5. 写入 `documents`。
6. 创建 `document_jobs`。
7. Redis 缓存任务进度。
8. 前端文档列表展示状态。

接口：
- `POST /documents/upload`
- `GET /documents`
- `GET /documents/{document_id}`
- `DELETE /documents/{document_id}`
- `GET /jobs/{job_id}`

验收：
- 上传 10 个合同样本。
- 文档列表能显示文件名、大小、状态、URL。
- 任务进度能从前端看到。

---

### 阶段 4：文档解析

目标：把文档解析成适合检索的结构化文本。

一期解析优先级：
1. PDF。
2. Word。
3. Excel。
4. Markdown/TXT。
5. PPT/OCR 作为增强。

PDF 解析建议：
- 先用 PyMuPDF 或 pdfplumber 做文本型 PDF。
- 合同样本先作为第一批解析验证资料。
- 解析时保留页码。

表格解析建议：
- Excel 用 openpyxl/pandas。
- PDF 表格可先做基础文本抽取，复杂表格作为 bad case 后续增强。

工作内容：
1. 实现解析器抽象接口。
2. 按文件类型路由解析器。
3. 产出 `content_text` 和 `content_md`。
4. 写入 `document_parse_results`。
5. 解析产物保存到 MinIO。
6. 计算解析质量分。
7. 前端支持解析结果预览。

接口：
- `GET /documents/{document_id}/parse-result`
- `POST /documents/{document_id}/reparse`

验收：
- 10 个合同 PDF 能解析出可读文本。
- 每段内容能保留页码信息。
- 解析失败能显示错误。

---

### 阶段 5：切片

目标：生成高质量 chunk。

切片策略：
- 优先按标题、条款、段落切。
- 合同类文档重点识别：
  - 合同主体。
  - 服务内容。
  - 交付时间。
  - 付款方式。
  - 验收条款。
  - 违约责任。
  - 保密条款。
- 每个 chunk 带文档名、页码、章节路径。
- 长段落设置 overlap。
- 表格 chunk 保留表头和上下文。

工作内容：
1. 实现 chunk 参数配置。
2. 写入 `document_chunks`。
3. 生成 PostgreSQL 全文检索向量。
4. 前端支持查看 chunk。
5. 支持重新切片。

接口：
- `GET /documents/{document_id}/chunks`
- `POST /documents/{document_id}/rechunk`

验收：
- chunk 不明显切断合同条款。
- chunk 能定位回文档和页码。
- 可通过关键词搜到对应 chunk。

---

### 阶段 6：向量化

目标：chunk embedding 入库，支持语义召回。

工作内容：
1. 封装 `text-embedding-v4` 调用。
2. 首次调用确认 embedding 维度。
3. 建立 `chunk_embeddings` 表。
4. 批量向量化 chunk。
5. 使用 `content_hash` 避免重复向量化。
6. 建立 hnsw 或 ivfflat 索引。
7. 支持重新向量化。

接口：
- `POST /documents/{document_id}/reembed`

验收：
- 所有 chunk 生成 embedding。
- pgvector 相似度查询可用。
- 重复内容不重复请求 embedding。

---

### 阶段 7：混合召回

目标：提高检索命中率。

召回路径：
1. 向量召回：pgvector。
2. 关键词召回：PostgreSQL 全文检索 + pg_trgm。
3. QA 召回：qa_pairs + qa_pair_embeddings。

融合策略：
- 初期使用 RRF。
- 保留每路召回分数。
- 记录召回来源。

工作内容：
1. 查询改写。
2. 多路召回。
3. RRF 融合。
4. 元数据过滤。
5. 检索调试接口。

接口：
- `POST /retrieval/search`

验收：
- 输入合同相关问题能召回正确合同 chunk。
- 检索调试页能看到 vector/keyword/qa 各路结果。

---

### 阶段 8：重排和上下文组织

目标：把最相关内容送入问答模型。

工作内容：
1. 封装 `qwen3-vl-rerank`。
2. 对融合后的 TopN 做 rerank。
3. 根据阈值过滤低相关内容。
4. 组织 final context。
5. 同一文档相邻 chunk 可合并。
6. 生成引用数据：
   - document_id
   - document_title
   - page_start/page_end
   - section_path
   - url

验收：
- Top5 结果相关性明显好于原始召回。
- 引用 URL 指向正确文档。

---

### 阶段 9：流式问答

目标：完成用户可用的 RAG 对话。

回答规则：
- 必须基于检索上下文。
- 证据不足时明确说明资料中未找到明确依据。
- 回答末尾展示参考来源。
- 来源必须含文档 URL。
- 回答后生成 0-3 个推荐追问。

工作内容：
1. 封装 `deepseek-v4-flash`。
2. 实现 SSE 流式输出。
3. 保存用户消息和助手消息。
4. 保存 retrieval_logs。
5. 生成推荐追问。
6. 前端逐字展示回答。

接口：
- `POST /chat/stream`
- `POST /chat`

SSE 事件：
- `message_start`
- `rewrite`
- `retrieval`
- `delta`
- `citations`
- `suggested_questions`
- `message_end`

验收：
- 用户提问后能流式返回。
- 回答末尾有参考来源和 URL。
- 回答后有最多 3 个推荐追问。
- 点击推荐追问可继续问。

### 阶段 12：评测和调优

目标：用样本资料建立准确度闭环。

评测集来源：
- 先基于 `10个合同` 自动生成和人工修正一批问题。
- 每个问题标注期望答案、期望文档、期望页码或 chunk。

评测指标：
- Top3 命中率。
- Top5 命中率。
- 答案正确率。
- 引用正确率。
- 来源 URL 可用率。
- 推荐追问可用率。
- 无依据问题强答率。

bad case 分类：
- 解析失败。
- 切片不合理。
- 向量召回漏召。
- 关键词召回漏召。
- rerank 排错。
- 上下文组织丢信息。
- 模型回答不准确。
- 引用 URL 错误。
- 推荐追问不相关。

调优顺序：
1. 先修解析。
2. 再修切片。
3. 再调召回。
4. 再调 rerank。
5. 最后调 prompt。

原因：
- 上游解析和切片错了，后面 prompt 再强也很难补。

## 6. LangChat/LangChain 使用边界

使用 LangChat/LangChain 的地方：
- LLM 封装。
- PromptTemplate。
- 文档处理链路的 Runnable 组合。
- query rewrite。
- answer generation。
- suggested questions generation。

不建议完全依赖 LangChat/LangChain 的地方：
- 数据库模型。
- 任务状态。
- 检索日志。
- 业务 API。
- 引用 URL 生成。

这些需要自己控制，便于调试和验收。

## 7. RAG 问答链路

```text
用户问题
  -> 读取最近会话上下文
  -> 查询改写
  -> 向量召回
  -> 关键词召回
  -> QA 召回
  -> RRF 融合
  -> rerank 重排
  -> 阈值过滤
  -> final context 组织
  -> deepseek-v4-flash 流式回答
  -> 追加参考来源和 URL
  -> 生成推荐追问
  -> 保存 conversation_messages 和 retrieval_logs
```

---

## 8. 推荐追问流程

```text
当前用户问题
  + 最终回答
  + 引用文档标题
  + 命中 chunk 摘要
  + 最近会话上下文
  -> 生成 0-3 个追问
  -> 去重
  -> 过滤无依据问题
  -> 返回前端
```

推荐问题示例：

```json
[
  {"question": "合同中对验收时间有什么要求？"},
  {"question": "如果延期交付会有什么责任？"},
  {"question": "付款需要满足哪些前置条件？"}
]
```

---

## 9. 来源 URL 生成流程

```text
上传文件
  -> MinIO 保存原始文件
  -> 生成 download_url
  -> 生成 preview_url
  -> documents 入库

检索命中 chunk
  -> 找到 document_id
  -> 读取 documents.source_url / preview_url / download_url
  -> 优先 source_url
  -> 否则 preview_url
  -> 否则 download_url
  -> citations 返回前端
```

前端展示：

```text
参考来源：
1. xxx合同.pdf，第 3 页，付款条款
   https://...
```

## 10. 任务执行方式

一期建议：
- FastAPI 接收任务。
- 后台任务或轻量 worker 执行解析、切片、向量化。
- PostgreSQL 持久化任务。
- Redis 缓存实时进度。

可选实现：
1. MVP 阶段：FastAPI `BackgroundTasks`。
2. 稳定阶段：独立 worker 进程。
3. 后续扩展：Celery/RQ/Arq。

建议一期采用：
- 初期先用独立 asyncio worker 或 FastAPI BackgroundTasks。
- 如果任务并发和稳定性要求提高，再引入专门队列。

## 13. 第一轮开发建议顺序

第一轮不要一次性做完所有细节，建议按这个顺序：

1. 建后端和前端项目骨架。
2. 写 Docker Compose：PostgreSQL、Redis、MinIO。
3. 写数据库迁移。
4. 做登录。
5. 做文档上传和 MinIO URL。
6. 做 PDF 解析。
7. 做 chunk。
8. 做 embedding 入库。
