# 部署运维文档

## 一、部署前准备

基础环境：

- Docker 和 Docker Compose。
- Python 3.11，用于本地开发或执行辅助脚本。
- PostgreSQL 16，生产建议使用独立数据库或 Java 服务器已有数据库。
- 数据库需启用扩展：`vector`、`pg_trgm`、`uuid-ossp`。
- Redis 7。
- MinIO 或兼容 S3 的对象存储。
- 可访问 DeepSeek 和 DashScope API。

必须准备的配置文件：

```powershell
Copy-Item .env.example .env
```

`.env` 中必须按目标环境修改：

- `DATABASE_URL`
- `REDIS_URL`
- `MINIO_ENDPOINT`
- `MINIO_ACCESS_KEY`
- `MINIO_SECRET_KEY`
- `SA_TOKEN_JWT_SECRET`
- `DEEPSEEK_API_KEY`
- `EMBEDDING_API_KEY`
- `RERANK_API_KEY`

注意：`.env` 不应进入代码交付和 Git 仓库。

## 二、本地 Docker 部署

本地联调使用 `deploy/docker-compose.yml`，该编排会启动 PostgreSQL、Redis、MinIO、backend、worker。

启动：

```powershell
cd D:\job_code\其他项目\南航项目\java_rag\deploy
docker compose up -d --build
```

查看服务：

```powershell
docker compose ps
```

查看日志：

```powershell
docker compose logs -f backend
docker compose logs -f worker
```

停止：

```powershell
docker compose down
```

清理本地数据卷需谨慎，会删除本地 PostgreSQL 和 MinIO 数据：

```powershell
docker compose down -v
```

## 三、远程 Docker 部署

远程部署使用 `deploy/docker-compose.remote.yml`。

特点：

- 只启动 Redis、backend、worker。
- 不启动 PostgreSQL。
- `DATABASE_URL` 从 `.env` 读取，应指向 Java 服务器已有 PostgreSQL。
- backend 端口默认暴露为 `18020`。
- worker 使用同一个镜像执行 `python -m app.workers.document_worker`。

启动：

```powershell
cd D:\job_code\其他项目\南航项目\java_rag\deploy
docker compose -f docker-compose.remote.yml up -d --build
```

查看：

```powershell
docker compose -f docker-compose.remote.yml ps
docker compose -f docker-compose.remote.yml logs -f backend
docker compose -f docker-compose.remote.yml logs -f worker
```

停止：

```powershell
docker compose -f docker-compose.remote.yml down
```

## 四、镜像构建说明

`backend/Dockerfile`：

- 从 `python:3.11-slim` 构建完整镜像。
- 安装 LibreOffice、字体、OCR 相关依赖。
- 安装 `requirements.txt`。
- 构建时间较长，但可在全新服务器直接使用。

`backend/Dockerfile.reuse`：

- 从 `rag-school-backend:runtime-base` 构建。
- 只复制业务代码，构建速度快。
- 目标服务器必须提前准备该基础镜像。

如果远程服务器没有 `rag-school-backend:runtime-base`，需要修改 `deploy/docker-compose.remote.yml` 的 `dockerfile` 为 `Dockerfile`，或先构建并推送 runtime-base。

## 五、数据库初始化和迁移

本地 compose 首次启动 PostgreSQL 时会执行：

```text
backend/sql/001_init.sql
```

该 SQL 会创建扩展、业务表和索引。

项目同时包含 Alembic 迁移：

```text
backend/alembic/versions/
```

生产环境建议统一使用 Alembic 管理结构变更。执行前请确认 `.env` 中 `DATABASE_URL` 指向目标数据库。

当前最新迁移包含：

```text
0010_internal_performance_indexes.py
```

该迁移会补充 internal 问答、权限过滤、会话、反馈和检索日志相关索引。升级前建议先备份数据库，升级后确认新增索引存在。

```powershell
cd D:\job_code\其他项目\南航项目\java_rag\backend
alembic upgrade head
```

如果生产数据库已由 `001_init.sql` 初始化，再执行 Alembic 前需要核对迁移版本表和现有结构，避免重复建表或结构漂移。

## 六、健康检查

服务启动后检查：

```powershell
curl http://127.0.0.1:8020/
curl http://127.0.0.1:8020/api/v1/health
```

Java 内部接口鉴权检查：

```powershell
curl http://127.0.0.1:8020/internal/rag/health `
  -H "Authorization: Bearer <Java Sa-Token JWT>"
```

成功响应格式：

```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "status": "ok",
    "name": "Java Internal RAG Service"
  }
}
```

远程部署可使用：

```powershell
python deploy\remote_health_check.py
```

## 七、运行日志

重点查看两个容器：

- `backend`：接口请求、模型调用、SSE、异常。
- `worker`：文档解析、切片、向量化、任务执行异常。

常用命令：

```powershell
docker logs -f rag_java_backend
docker logs -f rag_java_worker
docker logs -f rag_java2_backend
docker logs -f rag_java2_worker
```

本地 compose 容器名以 `rag_java_` 开头，远程 compose 容器名以 `rag_java2_` 开头。

## 八、对象存储桶

默认桶：

- `rag-documents`：原始文档。
- `rag-parsed`：解析后的 Markdown 或文本。
- `rag-preview`：OCR 图片、预览图片等。

如果桶不存在，需要由运维或应用初始化脚本创建。确认 `.env` 中：

- `MINIO_ENDPOINT`
- `MINIO_PUBLIC_BASE_URL`
- `MINIO_DOCUMENTS_BUCKET`
- `MINIO_PARSED_BUCKET`
- `MINIO_PREVIEW_BUCKET`

## 九、备份恢复建议

必须备份：

- PostgreSQL：业务索引、向量、日志、会话、反馈都在库中。
- MinIO：原始文件、解析结果、图片资产。

可不做强一致备份：

- Redis：主要是任务队列和缓存。生产环境如有正在执行的任务，重启后可能需要 Java 或人工重新触发处理。

备份策略建议：

- PostgreSQL 每日全量备份，重要上线前手动备份。
- MinIO 按桶做增量或对象级备份。
- 记录 `.env` 配置版本，但不要把密钥明文放入普通文档。

## 十、常见问题

### 1. `/internal/rag/health` 返回 401

检查：

- 请求头是否包含 `Authorization: Bearer <token>`。
- Java 传来的 token 是否是 JWT。
- `.env` 的 `SA_TOKEN_JWT_SECRET` 是否和 Java 端 `sa-token.jwt-secret-key` 一致。
- token 是否过期。

### 2. 文档一直是 `uploaded` 或任务不执行

检查：

- worker 容器是否运行。
- Redis 是否可用。
- `BACKGROUND_TASK_QUEUE_KEY` 是否一致。
- `document_jobs` 是否有 pending 任务。
- worker 日志是否有解析或模型异常。

### 3. 文档处理失败

检查：

- MinIO bucket 和 object_key 是否可读。
- 文件类型是否支持。
- 旧版 Office 是否需要 LibreOffice。
- OCR 是否耗尽资源或依赖缺失。
- 模型 API Key 是否有效。

### 4. 问答没有引用或提示没有可检索资料

检查：

- 文档状态是否为 `indexed`。
- `visible_in_chat` 是否为 true。
- Java 传入的 `access_scope` 是否过窄。
- `allowed_knowledge_ids` 是否匹配。
- `deny_attach_ids` 是否排除了目标文档。
- embedding 和 rerank API 是否正常。

### 5. 问答接口返回 429

说明当前聊天接口启用了并发槽位保护。

检查：

- `CHAT_MAX_CONCURRENT_REQUESTS` 是否过小。
- 多实例部署时 Redis 是否可用，`CHAT_DISTRIBUTED_CONCURRENCY_ENABLED` 是否符合预期。
- 是否有流式请求长时间未结束。
- 模型 API 响应是否过慢导致槽位占用时间过长。

### 6. Docker 构建很慢

原因通常是安装 PaddleOCR、PaddlePaddle 和 LibreOffice。可使用 `Dockerfile.reuse`，但前提是目标环境已有 `rag-school-backend:runtime-base`。
