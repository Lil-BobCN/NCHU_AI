# 系统说明文档

## 1. 系统目标

系统目标是把校内或项目资料沉淀为可检索、可引用、可持续评估的知识库。用户通过前端上传文档，系统自动解析并建立索引；问答时，系统从知识库召回相关片段，经过重排后交给大模型生成回答，并返回引用来源。

## 2. 用户角色

当前版本只实现管理员角色：

| 角色 | 权限 |
| --- | --- |
| 管理员 | 登录系统、上传和管理文档、管理知识库、管理 QA 对、发起问答、查看检索日志、提交反馈、维护评估样本 |

所有业务接口除健康检查和登录外，均需要 `Authorization: Bearer <token>`。

## 3. 主流程

### 3.1 文档入库流程

1. 管理员在前端上传文档。
2. 后端校验文件类型、大小和重复文件。
3. 原始文件保存到 MinIO 的 `rag-documents` bucket。
4. `documents` 表写入文档元数据。
5. 后端写入 Redis 任务队列。
6. worker 从 Redis 取任务并执行文档流水线。
7. 解析结果保存到 PostgreSQL 和 MinIO `rag-parsed` bucket。
8. 文本被切成 chunks，保存到 `document_chunks`。
9. 调用 embedding 模型生成向量，保存到 `chunk_embeddings`。
10. 文档状态更新为 `indexed`，可参与检索和问答。

### 3.2 问答流程

1. 前端调用 `/api/v1/chat/stream` 或 `/api/v1/chat`。
2. 后端创建或续接会话，保存用户问题。
3. 多轮场景下按配置进行查询改写。
4. 检索服务执行多路召回：
   - 向量召回
   - 关键词召回
   - QA 对召回
5. 召回结果去重、过滤、加权。
6. 调用 rerank 模型或本地规则重排。
7. 组装最终上下文和引用来源。
8. 调用问答模型生成回答。
9. 保存 assistant 消息和检索日志。
10. 前端流式展示回答、引用和推荐追问。

### 3.3 反馈和评估流程

| 功能 | 说明 |
| --- | --- |
| 回答反馈 | 管理员可对回答提交错误类型、描述和快照，保存到 `answer_feedbacks` |
| 检索日志 | 每次问答保存召回、重排、上下文、引用、回答和耗时 |
| 评估样本 | 人工维护标准问题和期望命中文档 |
| 评估批次 | 后台任务批量执行检索，计算 top3/top5 命中率 |

## 4. 功能模块说明

### 4.1 登录鉴权

| 页面/接口 | 说明 |
| --- | --- |
| 登录页 | 管理员输入账号密码 |
| `POST /api/v1/auth/login` | 返回 JWT |
| `GET /api/v1/auth/me` | 查询当前管理员 |

管理员初始化由 `python -m app.init_admin` 完成，默认读取 `.env` 中的 `ADMIN_USERNAME` 和 `ADMIN_PASSWORD`。

### 4.2 文档管理

支持：

| 功能 | 说明 |
| --- | --- |
| 上传 | 支持单文件上传，默认最大 100MB |
| 重复检测 | 可按文件名和 hash 判断重复 |
| 覆盖/保留副本 | 上传时可根据策略处理重复文件 |
| 文档列表 | 支持关键词、状态、知识库、批次筛选 |
| 导出 CSV | 导出文档清单 |
| 删除 | 逻辑删除并清理存储对象 |
| 批量操作 | 批量删除、批量知识库调整、批量重解析、批量重切片 |
| 旧 Office 转换 | `.doc`、`.xls` 转换为新格式后继续入库 |
| 压缩包导入 | `.zip`、`.rar` 安全解压并导入内部文件 |

### 4.3 文档解析

解析能力集中在 `backend/app/services/parse_service.py`。支持：

| 类型 | 说明 |
| --- | --- |
| PDF | PyMuPDF 提取文本，必要时 OCR |
| Word | `python-docx` 解析 `.docx`，旧 `.doc` 需 LibreOffice 转换 |
| Excel | `openpyxl`、`xlrd` 解析表格 |
| Markdown/TXT | 直接按文本解析 |
| 图片 | PaddleOCR 识别 |
| 压缩包 | 解压后导入支持格式文件 |

解析质量分会写入 `documents.parse_quality_score`，解析结果写入 `document_parse_results`。

### 4.4 切片和向量化

切片由 `ChunkService` 完成，关键配置：

| 配置 | 默认值 | 说明 |
| --- | ---: | --- |
| `CHUNK_SIZE` | 800 | 普通文本块大小 |
| `CHUNK_OVERLAP` | 120 | 文本块重叠 |
| `TABLE_CHUNK_ROWS` | 50 | 表格按行切片 |
| `TABLE_FULL_INDEX_MAX_ROWS` | 500 | 超大表格进入受限索引 |
| `MAX_DOCUMENT_CHUNKS` | 300 | 单文档最大切片数 |
| `MAX_EMBEDDING_CHARS_PER_DOCUMENT` | 200000 | 单文档 embedding 字符预算 |

向量化使用 DashScope OpenAI-compatible API，默认模型 `text-embedding-v4`，默认维度 `1024`。

### 4.5 RAG 检索

检索服务位于 `backend/app/services/retrieval_service.py`，核心策略：

| 策略 | 说明 |
| --- | --- |
| 向量召回 | 基于 pgvector cosine 距离检索 chunks |
| 关键词召回 | 基于 PostgreSQL 全文/模糊匹配 |
| QA 召回 | 对高频标准问答进行独立召回 |
| rerank | 调用 DashScope rerank 或本地调权 |
| 黑名单 | 通过 `RETRIEVAL_BLACKLIST_KEYWORDS` 过滤内部资料关键词 |
| 缓存 | Redis 缓存检索结果和回答 |

| 登录 | `frontend/src/views/LoginView.vue` | 管理员登录 |

## 5. 状态说明

文档状态：

| 状态 | 说明 |
| --- | --- |
| `uploaded` | 已上传，未处理 |
| `parsing` | 解析中 |
| `parsed` | 已解析 |
| `chunking` | 切片中 |
| `chunked` | 已切片 |
| `embedding` | 向量化中 |
| `indexed` | 可检索 |
| `failed` | 处理失败 |
| `deleted` | 已逻辑删除 |

任务状态：

| 状态 | 说明 |
| --- | --- |
| `pending` | 等待执行 |
| `running` | 执行中 |
| `succeeded` | 成功 |
| `failed` | 失败 |
| `skipped` | 已跳过 |
| `canceled` | 已取消 |

## 6. 关键配置说明

| 配置 | 说明 |
| --- | --- |
| `CHAT_MAX_CONCURRENT_REQUESTS` | 单进程问答并发 |
| `CHAT_GLOBAL_MAX_CONCURRENT_REQUESTS` | 分布式总并发限制，0 表示不限制 |
| `MODEL_REQUEST_TIMEOUT_SECONDS` | 模型请求超时 |
| `EMBEDDING_BATCH_SIZE` | embedding 批大小 |
| `RERANK_ENABLED` | 是否启用远程 rerank |
| `SIMILARITY_THRESHOLD` | 向量相似度阈值 |
| `RERANK_THRESHOLD` | rerank 阈值 |
| `ANSWER_CACHE_ENABLED` | 是否缓存回答 |
| `OCR_ENABLED` | 是否启用 OCR |

## 7. 系统边界

当前版本已覆盖 MVP 和交付所需的主要流程，但仍有一些边界：

1. 用户体系只有管理员，不包含多租户和细粒度权限。
2. 文档权限以知识库维度区分，未做用户级可见范围。
3. 问答质量依赖上传资料质量、解析结果、模型服务稳定性和 rerank 配置。
4. 生产环境的大规模数据导入需要分批执行，避免 embedding 速率限制。
5. Redis 队列不是强事务队列，重要批处理失败后建议从文档页面重新触发任务。
