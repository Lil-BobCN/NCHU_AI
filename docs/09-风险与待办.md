# 风险与待办

## 一、已知风险

### 1. 源目录不是 Git 仓库

当前 `D:\job_code\其他项目\rag_java` 不是 Git 仓库，无法通过 commit hash 标记交付版本。

建议：

- 正式交付后建立 Git 仓库。
- 首次提交标记 tag，例如 `handover-2026-07-10`。
- 后续所有改动通过分支和 Pull Request 管理。

### 2. 中文字符串存在编码乱码

部分代码中的中文错误信息、prompt 和注释已经乱码。编译检查通过，说明不影响 Python 语法，但会影响：

- 接口错误提示可读性。
- 模型 prompt 质量。
- 运维排障效率。
- 后续开发理解。

建议：

1. 先补齐回归测试。
2. 统一确认源文件编码为 UTF-8。
3. 分模块修复乱码文案。
4. 修复后重点回归问答质量和接口错误分支。

### 3. `.env` 未交付

这是正确做法，但接手方必须拿到真实配置才能部署。

必须线下交接：

- 数据库连接。
- MinIO 账号。
- Redis 地址。
- Java Sa-Token JWT 密钥。
- 模型 API Key。

### 4. `Dockerfile.reuse` 依赖外部基础镜像

`backend/Dockerfile.reuse` 使用：

```text
FROM rag-school-backend:runtime-base
```

如果服务器没有该镜像，远程构建会失败。

建议：

- 交付 runtime-base 镜像构建方式。
- 或远程 compose 改用完整 `Dockerfile`。

### 5. 远程数据库使用 Java 服务器已有 PostgreSQL

远程 compose 不启动 PostgreSQL，`DATABASE_URL` 必须指向现有数据库。

风险：

- 表结构和迁移版本不一致。
- RAG 表与 Java 业务表共库时权限需要隔离。
- pgvector 扩展可能未安装。

建议：

- 使用独立 schema 或独立数据库。
- 上线前执行结构核查。
- 建立备份和回滚方案。

### 6. OCR 资源占用较高

PaddleOCR 和 PaddlePaddle 对 CPU、内存、磁盘和构建时间都有要求。

建议：

- 远程低配机器先关闭 `OCR_ENABLED`。
- 如果业务需要扫描件识别，单独评估 worker 资源。
- 对超大 PDF 设置页数和文件大小限制。

### 7. 模型服务依赖外部 API

问答、embedding、rerank 均依赖外部模型 API。

风险：

- API Key 失效。
- 限流。
- 网络不可达。
- 模型名变更。
- 成本不可控。

建议：

- 监控模型调用错误率。
- 给 Java 侧提供友好降级提示。
- 对文档处理和问答设置并发限制。

## 二、待确认事项

- Java 端 Sa-Token JWT payload 的最终字段格式。
- Java 端附件 ID、文档 ID、知识库 ID 的字段来源。
- Java 端上传文件后，Python 是否直接读同一套 MinIO。
- 生产环境 RAG 服务访问地址和端口。
- 是否需要 HTTPS 或网关转发。
- 是否需要前端直接访问 Python 生成的文件链接。
- 文档删除时是否要求同步删除 MinIO 对象。
- 失败任务是否需要自动重试。
- 是否需要多租户隔离。
- 是否需要单独的管理员后台。
- 是否需要审计日志长期留存。

## 三、后续优化建议

优先级高：

- 修复乱码文案和 prompt。
- 给 Java internal API 增加更完整的契约测试。
- 明确 Alembic 和 `001_init.sql` 的唯一初始化策略。
- 完成生产 `.env` 配置基线。
- 建立 Git 版本管理和 tag。

优先级中：

- 增加任务失败重试和死信队列。
- 增加文档处理进度的 Redis 和数据库一致性校验。
- 增加 `/readiness` 对数据库、Redis、MinIO、模型 Key 的检查。
- 增加结构化日志和 request id 贯穿。
- 增加 Prometheus 指标或最小化监控指标。

优先级低：

- 建立管理后台页面。
- 支持更多文档格式。
- 支持多知识库独立参数。
- 增加离线评测报表。
- 增加模型供应商切换配置。
